# 怎样衡量协作是否有效

目标是衡量最终任务推进，工程回归与模型效果分开记录。

## 最小对照

使用同一程序版本、输入、模型与强度配置，分别比较：

1. 主模型直接执行。
2. 主模型执行加一次独立复核。
3. 现有独立分析、交叉审核与成果迭代循环。

每次从全新复制的工作目录和新对话开始，验收脚本放在模型不可见的独立评分目录。建议先选 6 个小任务，每种流程运行 3 次；这是一份可执行计划，本轮未启动这些付费调用。

| 场景 | 最终检查 | 希望观察的改进 |
|---|---|---|
| 数值函数 | 隐藏边界用例、原输入不变 | 发现并修复计算及异常行为 |
| 记录聚合 | 去重、作废、归属更改与输入校验 | 修复状态逻辑而非只改表述 |
| 统计解释 | 独立计算、混淆与因果边界 | 纠正结论且保留计算依据 |
| 来源核对 | 原始文本、日期、引文支持关系 | 找到同源转述和不支持的主张 |
| Word 修改 | 文档可读、指定内容、渲染及原件保留 | 实际文件改善与内容完整 |
| 专业软件输出 | 保存文件、目标对象/参数和工具回读 | 操作落地且交接后可继续使用 |

## 记录字段

- `case_id`、重复编号、流程、程序源码哈希、模型和推理强度。
- 初始成果和最终成果的独立验收结果。
- 审核提出的问题中，多少被外部检查确认，多少实际修复，是否引入新问题。
- 最终状态使用 `pass/fail/unknown/blocked`，并与程序的完成状态分别保存。
- 总耗时、调用数、接口报告的用量；只在核对计费规则后计算金额。

按任务类型比较收益。若一次复核已达到同样的成果质量，就优先使用更简洁的流程；对反复出现的能力瓶颈，再比较第三个模型是否带来增益。
